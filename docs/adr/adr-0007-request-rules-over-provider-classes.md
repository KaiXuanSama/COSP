# ADR-0007: 供应商差异用请求规则表达，不用专有 Provider 类

- **状态**：Accepted
- **日期**：2026-06-25（V8 完成专有 Provider 清理）
- **取代**：（无 —— 取代 V8 之前的「每供应商一个 Java 服务」做法）
- **相关**：[ADAPTATIONS.md](../architecture/ADAPTATIONS.md)（适配史与能力边界）、
  [KNOWN_DEBT.md](../architecture/KNOWN_DEBT.md)、
  [Claude Desktop 缓存 RFC](../working/rfcs/2026-10-17-claude-desktop-prompt-cache.md)

## 背景

V8 之前，项目为每个供应商（DeepSeek、MiMo、Kimi……）写专有 Java 服务类。这套做法在
供应商数量增长后暴露三个问题：

1. **每个供应商都要写代码、编译、发版**。改一个上游的特殊要求就要动 Java 代码
2. **能力与供应商名绑定**。`DeepSeekChatService` 里做的字段修正，MiMo 遇到同样问题时
   要么复制一遍，要么等到有人写 `MiMoChatService`
3. **无法由用户自助解决**。用户遇到上游不支持的字段时，唯一的出路是提 issue 等新版本

同时，真实世界的供应商差异其实很集中：**认证头不同**、**某些字段不收**、
**某些字段格式有要求**。这三类差异都不需要写代码——它们是**数据**。

## 决策

**所有供应商都是数据库配置，无内置/专有供应商实现。**

供应商差异用两类**声明式规则**表达，由用户在管理后台配置：

### 1. 请求头规则

覆盖 / 添加 / 通过 `/del/` 删除请求头，支持 `{apiKey}` 占位符。

### 2. 请求体规则组

按**规则组**组织，每组声明适用的线路协议（缺失视为全协议）。组内规则可：
- 按顺序修改、删除字段
- 递归调整对象/数组中的消息内容
- 字段值为数组时，「删除」作用于**匹配到的元素**（如按 `type` 摘掉上游不支持的工具）

**条件**：`exists` / `equals` / `matches`（正则包含匹配）
**操作**：`edit_object` / `set_value` / `delete` / `regex_replace`

### 3. 类型不靠猜

「设置字段值」与条件的「等于」都有**显式类型档位**（字符串 / 数值 / 对象或列表 / 布尔 / null）。
「等于 null」是可选项，而非留空的副作用。

「对象/列表」一档承载全部 JSON 结构体，因此可以整体替换一个对象
（如把 `text.format` 换成 `{"type":"json_object"}`，一次性丢掉 `schema` 等多余字段）。

### 4. 预览与生产同源

编辑器的转换预览由**后端生产引擎**计算，因此预览结果与实际发往上游的请求体出自同一份代码。

### 5. 正则用 Java 方言，保存时校验

条件的 `matches` 与操作的 `regex_replace` 都用 Java 正则（内联标志写在 pattern 里）。
**保存时编译一次**，非法直接报错——而不是运行时静默不生效（后者极难排查）。

运行时失败不抛异常：字段不存在静默跳过；字段非字符串、正则非法、替换文本非法
各产生一条结构化警告并保留原值。

## 后果

**正面**

- **新增供应商零代码**：配置即可，无需发版
- **能力随规则走而非随供应商名走**：同一个规则组可被多个供应商复用
- **用户自助**：遇到上游限制，用户自己加规则即可，不必等新版本
- **预览可信**：预览与生产同源，消除了"预览对了但实际发出去不对"这类问题
- 规则是**显式配置**，出问题时可审计、可回滚、可 diff

**负面**（知情成本）

- **规则引擎的能力边界就是适配能力的边界**。当某个供应商的差异无法用
  「条件 + 操作」表达时（如需要跨字段逻辑推导、需要调用外部服务），只能扩展引擎
  或退回写代码
- **规则复杂后难以维护**。一个供应商可能需要多个规则组、每组多条规则，
  依赖顺序且互相影响。本项目的 MiMo 预设就是例子：三个规则组、
  每条都来自实测的上游硬拒绝
- **正则规则的方言限制**：前端只校验正则非空、不用 JS `RegExp` 编译，
  因为两种方言不一致（所有格量词 `a*+` 只有 Java 支持）。这意味着用户写错正则时
  要到保存时才被后端拒绝
- **调试成本转移给用户**：规则写错时的现象是「请求被上游拒绝」，而不是明确的规则错误

## 备选方案

### 方案 A：保留专有 Provider 类，按供应商名分发

- 描述：每个供应商一个类，代码里处理其特殊要求
- 拒绝理由：**每个差异都要发版**，且能力被供应商名锁死。这正是 V8 清理掉的做法。
  更关键的是，用户无法自助——这在一个需要持续接入新供应商的代理项目里不可接受

### 方案 B：用配置文件（YAML/JSON）描述供应商差异

- 描述：启动时读取配置文件，按配置调整请求
- 拒绝理由：配置文件**改动需要重启**且不便于用户在 UI 里编辑与预览。
  数据库 + 规则引擎方案支持在线编辑、即时预览、按供应商/模型粒度生效

### 方案 C：让用户自己写脚本（钩子函数）

- 描述：提供脚本接口，用户写 JS/Groovy 处理请求
- 拒绝理由：**任意代码执行的安全风险**，且脚本难以审计与预览。规则引擎的表达力
  已覆盖实测到的全部供应商差异（包括正则这类较复杂的场景）

### 方案 D：只做请求头规则，不做请求体规则

- 描述：只解决认证差异，字段差异让上游自己报错
- 拒绝理由：实测的供应商差异里**请求体问题占多数**（MiMo 拒收 `web_search`、
  只接受特定 `text.format`；Claude Desktop 的 `system` 缓存断点）。不处理请求体
  就等于把大部分适配问题留给用户
