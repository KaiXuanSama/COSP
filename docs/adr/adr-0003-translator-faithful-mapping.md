# ADR-0003: 翻译器只做字段搬运，不做推导与自动修正

- **状态**：Accepted
- **日期**：2026-09-03（C2M 契约首次入库）
- **取代**：（无）
- **相关**：[C2M 请求契约](../reference/contracts/C2M-REQUEST-CONTRACT.md)、
  [C2M 响应契约](../reference/contracts/C2M-RESPONSE-CONTRACT.md)、
  [RFC 协议翻译](../working/rfcs/2026-09-03-protocol-translation.md)

## 背景

跨协议翻译时，下游字段与上游字段不是一一对应。面对缺失或语义不对齐的字段，有三种取向：

1. **补默认值**：下游没说 `max_tokens`，翻译器填一个合理值
2. **自动修正**：发现值可能不被上游接受（如过小的 `max_output_tokens`），clamp 到合法范围
3. **原样搬运**：下游说什么就翻译什么，缺了就缺着，不合规就交给上游报错

这三种取向会导致**截然不同的可观测行为**，而问题在于：一旦翻译器开始"帮忙"，
用户就无法判断某个上游错误到底是自己的配置问题，还是代理悄悄改了参数。

更要紧的是**责任边界**：本项目已有一整套「设置层」（思考深度、最大输出的四档注入模式）
专门负责补默认值。如果翻译器也补，就会出现两处在做同一件事，且优先级难以推理。

## 决策

**翻译器只做字段搬运（faithful mapping）：不补默认值、不做范围修正、不凭空增删字段。**

三条具体推论：

| 场景 | 决策 | 理由 |
|---|---|---|
| 下游没说 `max_tokens` | **不补** | 补默认值是设置层（`MaxOutputTokensSetting` 四模式）的职责。翻译器补会和它冲突 |
| 值可能不合法（如 `<16`） | **不 clamp** | clamp 属「自动修正」。上游对非法值会自己报错——让错误可见优于静默修正 |
| 上游才有的字段（如 Responses 的 `web_search`） | **不合成** | 下游没传就是没传。增删交给请求体规则（用户显式配置），不交翻译器猜 |
| 字段改名后原字段是否保留 | **按方向分别决定**（见下） | 取决于下游是否有"表态判定"逻辑依赖旧字段 |

### 关于「改名后是否删原字段」

这不是一刀切的规则，而是**逐方向判断**：

| 方向 | 处理 | 依据 |
|---|---|---|
| C2M（`max_tokens` → `max_tokens`） | 保留（同名） | 无改名 |
| C2R（`reasoning_effort` → `reasoning.effort`） | **删原字段** | `applyToResponses` 的表态判定只看 `reasoning.effort`；保留旧字段反而可能被 Responses 上游拒绝，且这条线没有 MESSAGES 侧那样的收尾清理方 |

判断标准是：**改名后，下游是否还有代码依赖旧字段名？** 有则保留，无则删除。

## 后果

**正面**

- 上游错误可直接归因到用户配置，不存在「代理偷偷改了参数」这类玄学
- 设置层的职责边界清晰：所有默认值注入集中在一处，可枚举、可测试
- 翻译器行为可用「字段映射总表」完整描述——每个下游字段对应一个上游字段，没有隐藏逻辑

**负面**（知情成本）

- **用户可能看到更"原始"的错误**。例如上游对 `<16` 的 `max_output_tokens` 报错时，
  用户需要自己理解这是参数问题，而不是被代理悄悄修正后"看起来正常但效果不对"
- **需要设置层真的覆盖到每个方向**。C2R 初期的 `max_output_tokens` 就是典型：
  RESPONSES 侧没有对应支线，而 CHAT 直连不注入也不补——这被记为已知缺口（RFC-1 §C6），
  而不是在翻译器里临时补上
- 翻译器代码里会有大量「if 字段存在则搬运」的样板，读起来不如"聪明"的实现紧凑

## 备选方案

### 方案 A：翻译器兜底补默认值

- 描述：下游没传时填一套「安全默认值」，保证上游总能收到完整请求
- 拒绝理由：与设置层职责重叠，两处补值会产生难以推理的优先级；且"安全默认值"无法定义——
  对长上下文模型和对小模型的安全值不同，最终只能按模型名猜，违反「不硬编码模型能力」

### 方案 B：翻译器做参数校验与 clamp

- 描述：发现非法值时修正到合法范围，提高成功率
- 拒绝理由：**静默修正比报错更难排查**。用户看到一个成功响应，但实际用的不是他配置的参数——
  这类问题在现场几乎无法定位（本项目的 `KNOWN_DEBT.md` 记录过同类教训）

### 方案 C：翻译器透明转发未知字段

- 描述：下游传了什么就全量透传，包括目标协议不认识的字段
- 拒绝理由：Responses 与 Messages 对未知字段的处理不一致（部分严格报错），透传会让
  「下游能跑、换成另一个上游就失败」成为常态。**只搬运有明确映射的字段**是更可预测的契约
