# ADR-0012: M2C 去程采用忠实映射与显式损失边界

## 背景

Claude Desktop 成为常用客户端后，`/v1/messages` 需要能接入只提供 Chat Completions 的上游。
现有 C2M 请求与 M2C 响应属于另一条链；本次需要的是声明 `(MESSAGES, CHAT)` 的
M2C 请求与 C2M 响应，不能因缩写相同而误认方向已实现。

请求层的难点不是注册一个译器，而是**哪些信息能等价表达，哪些会无声改变下游意图**：
文档源类型多于 base64，工具结果可含媒体和错误标志，思考明文与签名不同，
合法空工具结果也不同于缺少应答。静默删除这些内容可能得到一个正常响应，
但模型实际没有看到用户交付的文件或工具状态。

参考项目提供了可行先例，却没有完全一致的处理规则。官方 Chat 定义已有 `file` part，
但 `tool` 消息并没有 `name`；某个参考项目发送一个字段，不能证明严格上游要求它。
需要按协议事实和本项目边界决定，而不是整套照抄。

## 决策

**M2C 去程采用无状态的忠实结构映射；能直接表达的内容保留，已确认无法等价表达的
内容或执行要求显式失败，必要的已知元数据允许确定性编码，但不伪造内容。**

### 1. 保留既有职责边界

M2C 译器是新增支线，system 落回消息数组由独立 CHAT system 归一化支线负责。
路由、直连优先、C→M→R 回退顺序、请求体规则的最终决定权、鉴权配置与重试机制均不重定义。
不推导 token 默认值或预算档位，不按模型名猜能力。

流式请求由本方向主动索取上游 usage；这是保持记账所需的协议选项，
不是替用户增加生成参数。它不扩展到所有直连 CHAT 请求，也不能压过后续用户规则。
回程如何渲染 usage 不得改变上游原生记账槽，具体算法留给回程阶段。

### 2. 文档和显式格式意图不静默降级

首版范围包含可纯结构转换的内联文档、文本/content 源、工具结果内文档及 JSON Schema 输出。
不通过下载、上传、PDF 解析或另建文件存储实现这些转换。

URL 文档、跨服务文件 ID、引用定位要求和无等价执行能力的服务端工具，
不能通过丢弃内容或伪装成普通函数让请求“看起来成功”，应显式报错。
目标上游不支持已正确映射的 file/schema 时，保留可理解的失败，不自动换协议或篡改内容。

### 3. 工具历史以因果配对为准

Chat tool 消息默认不发 `name`，以 `tool_call_id` 配对。
清理未得到应答的工具调用，孤儿结果丢弃并留痕；重复 ID 报错，不随意择一。
**真实空结果仍是已应答**，不能因为正文为空就删除结果及其调用。

保留有效结果的邻接与媒体来源，不把目标 Chat 消息强制整理成 Anthropic 的角色交替形态。
这一选择承认不完整工具历史可能被清理，但避免以伪造应答填平缺口。

### 4. 允许编码已有元数据，不允许编造返回内容

`is_error` 与工具媒体归属在 Chat 中没有相同外壳字段，允许使用最小、固定的文本标记
保留这些**已经存在的事实**；媒体在本组工具结果之后输出，来源仍可识别。
真正空结果不添加虚构的 `(empty)` 返回内容。

这不取代 ADR-0003：它是原数据的确定性编码，不是补写新工具结果、生成思考或增加未请求的功能。
标记的具体文案不是本 ADR 的冻结内容，属于目标契约与实现测试。

### 5. 历史思考只搬已有明文

带有效工具调用的 assistant 轮回放请求中已有的 thinking 明文；不要求代理生成有效 Anthropic 签名。
没有明文不造占位，纯文本轮不回放；不重建已删除的跨请求思考缓存。
配对清理后是否仍有工具调用，应与回放范围保持一致。

### 6. 首版不自动翻译缓存策略

丢弃协议层 `cache_control`，不自动生成 `prompt_cache_key` 或新版显式缓存断点。
保持转换结果和稳定历史的确定性，缓存实际效果由目标上游决定，不承诺命中率不变。

理由不是“Chat 永远没有显式缓存 API”，而是任意兼容上游的字段、TTL 和能力并不统一；
本次不增加模型能力硬编码或新配置系统。未来若需要更完整的缓存控制，另作决策。

### 确认范围

以上是已确认的策略。RFC 中关于末尾 assistant prefill、部分工具扩展字段、
服务端容器的值级边界和具体包装常量仍有工程建议/待确认项，**不由本 ADR 顺带批准**。
目标字段与待确认状态分别见请求契约、RFC；Accepted 表示决策已确认，**不表示功能已实现**。

## 后果

**正面**

- 文档和工具上下文不会因静默丢块而伪装成成功，错误能定位到字段。
- 纯结构转换不增加远程文件 I/O、数据库状态或供应商专有实现。
- 既有主干、规则和调度可复用，新增方向与旧方向的行为边界清晰。
- 工具空应答、缺失应答、重复应答分开处理，测试可以覆盖明确的状态矩阵。

**负面**

- 一些在 Messages 原生端点可用的功能会被明确拒绝；此方向不承诺完整 Messages 协议覆盖。
- 清理未应答调用会减少不完整历史，必须留痕；固定元数据文本也会增加少量 token。
- file、reasoning、严格 schema 的实际兼容性仍依赖上游，需真实客户端验证。
- 只完成去程时，正常 Chat 响应仍无法满足 Anthropic 下游；半轮只适合功能分支内受控验证，
  不能独立当作可发布功能。

## 备选方案

### 全面照抄某个参考项目

拒绝：各家的兼容开关、签名处理、媒体提示、schema 清洗不同；局部转换函数也未必是最终出站行为。
照抄会引入模型硬编码或静默参数修正，与本项目配置驱动的边界冲突。

### 对所有无对应字段静默丢弃

拒绝：丢掉文档、错误状态或执行要求后仍可能得到 200，用户却无法知道输入语义已变。
允许省略的辅助元数据不能成为删除正文的理由。

### 默认添加 tool.name、空结果和 reasoning 占位

拒绝：非官方字段不能当成严格兼容的必需项；伪造返回/思考掩盖输入缺口。
已有错误或媒体来源的编码与“补一个看起来合理的值”有明确区别。

### 通过文件下载、OCR、缓存或自动改道补齐所有能力

拒绝：扩张 I/O、凭据和状态边界，不再是请求体翻译；还会改变计费与失败语义。
相关能力必须另行设计，不能隐藏在本支线内。
