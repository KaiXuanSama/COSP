# ADR-0010: 刻意不做的技术债清单与判断原则

- **状态**：Accepted
- **日期**：2026-09-19 前后（清单建立）
- **取代**：（无）
- **相关**：[KNOWN_DEBT.md](../architecture/KNOWN_DEBT.md)（活文档，逐条明细在此）、
  [AGENTS.md](../../AGENTS.md)

## 背景

代码审查会持续发现「看起来该修」的问题。但不是每个问题都该在当前分支修——有些是：

- **修复成本高于收益**（如为一个已稳定的类抽公共基类）
- **修复本身会引入更大风险**（如运行时自动改写用户的存量配置）
- **当前信息不足，需要先观察**（如某个上游的真实行为尚未稳定）
- **刻意保留的重复**（如三侧服务不共享基类，因为形态差异大于共性）

问题在于：如果这些问题不留痕，它们会被**反复提出**——每换一个人审查就要重新辩论一次
「为什么这里不改成 XX」。

## 决策

**建立 `KNOWN_DEBT.md` 作为「经审查确认、刻意不处理」的清单**，每条必须写清：

1. **现象**：问题是什么
2. **为什么不修**：具体的取舍理由（不是"以后再说"）
3. **影响面**：不修会导致什么
4. **弃置条件**：什么情况下应该重新考虑（可选）

### 判断原则（写入文档首节）

| 原则 | 含义 |
|---|---|
| 修债前先查清单 | 避免重复讨论已定案的事 |
| 「不做」也是决策 | 与「做」同等重要，需要记录理由 |
| 弃置条件要具体 | 「将来再看」不算理由 |
| 已解决的要标记 | 保留条目并标注 **已解决** / **已还**，不直接删除（历史可查） |

### 配合 AGENTS.md 的 TODO 约定

**已经做出的取舍不留 `TODO`**——`TODO` 只标记「待做的事情」，取舍归本文档。
这条约定防止 `TODO` 变成「既不知道要不要做，也不知道为什么没做」的垃圾堆。

## 后果

**正面**

- 审查者不必重复辩论同一个问题
- 「不修」的理由被固化，将来环境变化时可以准确判断是否该重新考虑
- 已解决项保留标记（如「十、落库那一族的跨协议合并 —— **已解决**」），
  历史可追溯

**负面**（知情成本）

- **清单会腐烂**：代码变了但清单没更新时，条目会描述已不存在的现象。
  缓解措施是把它当活文档维护（每次审查时顺手核对）
- **可能变成「免责声明」**：如果什么都往里塞，就失去了「经审查确认」的严肃性。
  判断原则里强调「弃置条件要具体」就是为了防止这一点
- **需要定期复审**：弃置条件触发时（如上游行为稳定了）要回来处理，
  但没有机制自动提醒

## 备选方案

### 方案 A：不留清单，直接在代码里写 `TODO` 注释

- 描述：问题就地记录，不建文档
- 拒绝理由：`TODO` 无法承载「为什么不做 + 影响面 + 弃置条件」这些结构化信息；
  且分散在代码里无法一次性浏览全貌。本项目已明确「取舍不留 `TODO`」

### 方案 B：开 GitHub issue 跟踪

- 描述：每个不修的问题开个 issue
- 拒绝理由：issue 适合「打算处理」的事项；刻意不做的取舍开 issue 会污染 backlog，
  且 issue 的格式不适合承载取舍理由。**本地文档更适合"已定案"的记录**

### 方案 C：修掉所有发现的问题

- 描述：不留债，审查发现即修
- 拒绝理由：**修复本身有风险**。例如「不抽三侧上游服务的公共基类」——抽基类会让
  Chat/Messages/Responses 三条差异明显的线路被迫共享抽象，这是负收益的重构。
  另如「存量错误配置不做自动改写」——自动改写用户数据是不可逆操作
